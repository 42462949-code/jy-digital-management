# 用户与权限版本部署说明

此目录是可运行的 PostgreSQL 企业后台。旧 GitHub Pages 仍为本机模式；只有经此后台同域提供的网页才启用真实用户与权限。不能把静态网页上的按钮隐藏当成后台鉴权。

## 服务器准备

建议起步配置为2核、4GB内存的Linux服务器，按实际数据量和人数调整。准备一个解析到服务器的域名，安装Docker与Compose，开放HTTPS所需的80/443端口。数据库不映射到公网。

在当前项目根目录执行：

```sh
cp enterprise/.env.example enterprise/.env
```

填写 `JY_DOMAIN`、随机数据库密码 `JY_DB_PASSWORD`、初始管理员账号与密码。数据库密码建议使用随机十六进制字符串，避免URL转义问题；初始账号密码至少10字符。不要把`.env`提交到仓库或发到聊天中。

```sh
docker compose --env-file enterprise/.env -f enterprise/compose.yaml up -d --build
```

访问 `https://所填域名`。初始管理员第一次登录必须改密。初始化只在用户表为空时执行，不会因重启覆盖已有用户密码。

## 初始化与迁移

1. 指定一台浏览器作为正式主数据，不自动合并各电脑的独立数据。
2. 在原网站同一浏览器打开 `migration-export.html`，导出含各表、信息录入、工单批次标识与扫码状态的JSON备份。备份不含密码，也不删除原数据。
3. 企业版登录后进入“系统设置 → 数据迁移”，上传备份，核对记录数、重复销售ID及班组名称等冲突，再明确点击确认。
4. 后台已有数据时拒绝覆盖迁移；相同迁移文件重复提交不会重复新增。历史记录默认归属迁移管理员，原班组按名称关联。需要时，选中记录后使用管理员的“分配归属”。
5. 在生产班组表维护基础资料，随后建立员工账号、指定班组与岗位角色。角色矩阵支持查看、新增、修改、删除、导入导出、标签与报表打印，以及下推、草稿、确认、报工提交等专用权限。
6. 用不同岗位账号验证完整流程，再通知员工切换到新网址。新后台作为唯一正式数据源，避免继续在旧网站同时修改。
7. 切换前保管迁移备份。正式切换后，应停止旧网站发布业务数据文件，并处理旧公开发布资源；本部署镜像不包含发布数据压缩包，后台也拒绝公开下载该类文件。

## 业务规则

- 关闭订单使用闭锁图标，“取消关闭”使用开锁图标；取消关闭恢复原状态，无历史状态的订单恢复为“审核”。两项操作可分别授权并记录日志。
- 企业版需要联网访问后台；断网保存会报错并保留待处理状态，不能当作离线已提交。
- 同一订单可分批下达：按订单子表ID累计所有工单数量，默认下推剩余数量，确认时在数据库事务内再次检查，拒绝超量。
- 工单确定同时生成工单、追加销售打印记录并结清草稿；重复确认不重复生成。
- 标签统一宽100mm、高80mm，四周2mm留白。返回后由用户确认“已打印，清空本次信息”，只清空原表本批次且未改变的录入；不能据浏览器打印事件推断实际出纸成功。
- 考勤生产组别每次打开读取最新生产班组非空值。
- 账号停用立即撤销会话；权限每次操作重新校验，不能通过粘贴、直接请求或旧页面绕过。
- 草稿、正式数据与权限都在后台；本机只保存按用户隔离的界面偏好，退出会清理当前内存数据。
- 导出、标签和报表打印遵守对应数据范围。复制遵守查看范围；查看过的内容无法靠网页禁止截图或手动摘录。
- 已提交扫码记录禁止普通编辑和删除；另授“更正已提交报工”权限的主管可填写原因后更正，日志保留前后内容。日志由后台记录真实账号和时间，不能由“制表”文字代替。

## 备份与恢复

定期备份PostgreSQL，备份文件需要妥善保管。示例：

```sh
docker compose --env-file enterprise/.env -f enterprise/compose.yaml exec -T database pg_dump -U jiayang -Fc jiayang > jiayang-backup.dump
```

恢复前停止应用写入、保留当前数据库备份，并在单独环境验证恢复结果，不直接覆盖运行中的正式库。

服务器管理员重置密码：

```sh
docker compose --env-file enterprise/.env -f enterprise/compose.yaml exec app python -m enterprise reset-password --username admin
```

控制台交互输入新密码，命令不会把密码写到参数或日志；被重置用户下次登录必须改密。

## 测试与开发

运行依赖固定在`requirements.txt`，测试环境安装`requirements-dev.txt`。自动测试使用独立PostgreSQL测试库，设置`JY_TEST_DATABASE_URL`后执行`pytest enterprise/tests`。测试会清空该测试库，绝不能指向正式数据库。

本机开发允许显式设置`JY_DEVELOPMENT=1`和本机HTTP来源；正式环境必须使用HTTPS，不能启用开发选项。不要把`backend/`中的旧单账号扫码服务与本后台同时作为正式数据源。

部署包不包含原系统业务数据文件、实际账号密码或数据库。管理员按迁移页面核对后再导入真实数据。

## 考勤、单价与产值统计

考勤行号等于服务器记录 UUID，录入人和时间由后台生成；并发新增使用独立记录，修改核对版本并执行个人/班组/部门范围权限。正常工时折算采用正常班＋平时加班×1.5＋周末加班×2。单价表索引10，审核/反审独立权限 `approve_price` / `unapprove_price`；相同四项业务键最多一条已审核价格。已审核记录不能经编辑、删除、粘贴或导入覆盖。

手工报工以工单信息录入数量为准，须提交日期、部门及有效班组；数量累计、清空信息录入、生成带单价金额的生产记录在同一事务完成，并支持请求重试幂等。扫码确认由来源工单取得单位及定价四项字段，使用已审核价格；未匹配金额留空，授权用户可补单价，后台重新计算金额。

统计索引11为虚拟报表，`view`、`export` 和目标 `update` 分别授权。后台每天越南时间10点冻结来源，首次启动时也建立当时快照；未运行期间无法定时抓取历史状态，补启动时使用可取得的数据。按冻结数据的归属筛选权限后再汇总，用户不会取得其他范围的明细。目标按月份全公司共用，修改保留日志。按最新要求停用原库存5/6的目录、接口及权限，仅开放模板表12/13，名称为即时库存和出入库明细表；原角色的相应权限迁到新版表，已有新版授权优先保留。数据库启动自动补齐旧生产单价/金额及考勤系统列；迁移兼容旧10槽和新14槽备份，并跳过空白考勤模板行。

## 20261102 工时、关联价格、库存与节点权限

销售原27字段升级为29字段（末尾币别、单价），生产原20字段升级为22字段（原订单数量位置改客户指令单，末尾规格、币别），旧导入仍可接收。考勤单价固定3及成本由服务器生成。销售按已审核价格四项键定价；生产按销售ID取得指令及规格，再按四项键定价。派生字段在事务内更新并返回最新版本，客户端没有源表权限时不得自行重算为零。

单价表行号为服务器序列分配的递增唯一数字，内部记录仍使用UUID和独立版本；两者分别保证新增不冲突和修改不覆盖。既有UUID行号在启动时迁移为数字，不改变记录内部ID或审核信息。生产历史订单数量在升级时不作为客户指令显示，能找到来源时填入真实指令。

库存六项键不含物品编码，重复库存允许暂存以供人工核对，但不能用重复来源生成单据。`POST /api/inventory/post-voucher` 需要库存表的 `generate_inventory` 节点权限，校验每行版本、原信息录入、仓库及数量，在单一事务内写明细、清空来源并更新库存；请求ID保证重试幂等。退货方向按单据类型变号。余额按用户当前可见排序投影计算，不能以客户端上传余额作为依据。

用户与权限表索引14，由 `POST /api/access/rows` 的管理员接口维护，通用同步接口不允许直接改写此表。密码写入Argon2哈希到账号表，权限行只保留掩码，日志不记录密码，导出也不包含哈希。显式节点禁止优先于允许及原角色授权；未显式配置的节点沿用原角色，新增账号默认无角色。管理员账号保护仍有效，普通账号无论权限行如何填写都不能管理授权。删除新建账号的最后一条权限时停用该账号并撤销会话。迁移工具跳过只有脱敏密码的权限行，需管理员通过新界面导入并设置初始密码。

库存首次入账规则：同一六项键的物品尚无台账时，首笔单据带入该物品的库存期初数；后续单据期初填0，避免重复累计。已有台账不重复带入。
